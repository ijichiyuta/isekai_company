# ADR-0001: balance ハッシュとセーブ互換の結合

**状態**: 採択 / **日付**: 2026-08-26 / **関連**: 要件 §2.2, §8.2, §16.2, §17.1、M0監査 P3

## 背景

セーブは `balance_hash`（`assets/balance/*` 全体のコンテンツハッシュ）を保持し、`decodeSave` は現行 balance と不一致なら拒否する（`SaveCorruptException`）。これは「同一ビルド＋同一 balance ハッシュ内でのみリプレイ互換」という §2.2 rule 7 の境界を守るための仕組み。

一方で M2 で recipes を 11→75 に拡張すると balance_hash が変わり、**既存セーブが全滅**する。M0 監査（P3）はこの密結合をリリース前に方針決定せよと指摘した。

## 決定

1. **MVP（プレイテスト前）**: balance 変更でセーブ非互換になることを許容する。TestFlight 前の開発中はセーブ破棄で構わない。`decodeSave` は不一致を拒否し、アプリ層は 3世代バックアップ→なければ新規ライフで開始する。
2. **リリース後の balance 調整**: balance JSON は**追記のみ**を原則とする（既存 id の意味・数値の破壊的変更をしない。新レシピ/素材は末尾 id 追加）。これにより「発見済み recipe id」等のセーブ参照が保たれる。
3. **balance_hash の役割を「厳密一致ゲート」から「マイグレーション判定キー」へ格上げ（v1.0）**: セーブに balance の `schema_version` と `content_hash` を記録し、ハッシュ不一致時は即拒否ではなく **balance マイグレーション表**（recipe id 再マップ等）を引く。マイグレーション不能な場合のみ拒否。これは `saveMigrations`（ADR未番号・save.dart）と対をなす balance 版マイグレーション機構。
4. **リモート配信（v1.0以降）**: balance のリモート上書きは「数値のみ・転生境界で適用」に限定（要件 §16.2）。構造（id 割当）を変えるリモート配信は行わない。

## 帰結

- **良**: MVP は単純（不一致＝破棄）で実装コストゼロ。追記のみ原則で、リリース後の通常運用（レシピ追加）はセーブを壊さない。
- **悪**: MVP 開発中は balance を変えるたびテストセーブが消える（開発上は許容）。
- **要フォロー**: v1.0 で balance マイグレーション表の枠を `save.dart` の `saveMigrations` と同様に用意する（AC-15 の balance 版）。M2 で recipes を拡張する際、id を「追記」に徹する運用を守る。
