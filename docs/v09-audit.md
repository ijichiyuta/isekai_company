## v0.9-C 流行真edge 調査（試行→reverted、honest記録）

V-1の「流行タイミングの手動優位が未実現」を直すため、**流行を「カテゴリ固有の排他ボーナスプール（そのカテゴリを生産した者だけが取得・取り逃すと消失）」へ改修**を試みた（weightOfから流行倍率を除去し、water-fill後に排他bonus pool追加）。結果：
- **失敗（reverted）**。attackのtrendAware ON/OFF差は依然 **0%**。根因は sales模型でなく **botの過剰在庫**：botは各ラインを pool×4 週分保持するため、trend-blind botも流行カテゴリの在庫を常に十分持ち、排他ボーナスを自動捕捉してしまう。ボーナスがどんなに大きくても過剰在庫（≈124×pool）を超えられない。
- さらに **AC-10が+12%→+9-10%に悪化**（一部seed FAIL）＝ボーナス総需要増で攻めの相対edge（積極運用差）が希釈。目標未達＋回帰のため**engine/gateをrevertし v0.9-B状態を維持**（AC-10 +12%・AC-09 101-112%）。
- **真の解決に必要なもの（v0.9続き・honest）**: 流行edgeを bot計測可能にするには **botの在庫戦略を「需要近傍生産（過剰在庫しない）」へ再設計**する必要があり、これは経済全体の再校正を伴う大改修。現行の共有プール＋過剰在庫モデルでは、流行タイミングは bot metric上 no-op。実プレイヤー（選択的に生産）は流行生産で得をするが、headless AC-10 では表現不能。**AC-10の+10-20%は積極運用差で達成（達成済・honest）**とし、流行タイミングの手動優位は在庫モデル再設計時に再訪。

## v0.9-D 需要近傍生産 調査（試行→reverted、honest記録・2026-08-28ループ）

v0.9-C の revert 根因（bot過剰在庫で流行edge計測不能）を直すため、**produce loop を「総在庫を desiredTotal=pool×(1+headroom) に保つ deficit-replenish（需要近傍生産）」へ改修**（従来は per-line 上限 pool×3 のため総在庫≈N_lines×pool×3 に累積）。200ライフでゲート測定した結果：

- **HARDゲートは全PASS維持**（AC-04/05/07/08）。
- **AC-09 が §10.2 の 3〜5.5倍へ暴騰**（400w:353% 1000w:556% 1800w:284% 2600w:135%）。根因＝**旧・過剰在庫が「死に在庫の素材費」として大量の現金を暗黙にシンクしていた**。需要近傍化でその浪費が消え、bot は 3-5倍 capital-efficient に。＝§10.2 校正は暗に過剰在庫の浪費に依存していた（脆い校正）。
- **AC-10 が +11%→+4% に低下（FAIL）**。過剰生産の優位が消え、放置(idle)が攻め(attack)とほぼ同効率に。「能動プレイが+10-20%勝る」設計要件を割る。
- 流行edge（trendAware ON/OFF）は未測定のまま。

**判断（ループの規律）**：HARDは通るがソフト2本が設計退行（funds暴騰・aggression edge消失）。これは**価格/コストの全面再校正＋trend-pool(v0.9-E)＋§10.2再定義を要する設計級の変更**で、無人ループで安全に収束させられる範囲を超える（＋「より高収益・高速progressionの経済を是とするか」はユーザー判断）。よって**base_bot.dart を revert し green baseline を保持**。near-demand経済を採るなら、①価格/賃金/コスト再校正で funds を §10.2 へ戻す ②v0.9-E trend排他プールで AC-10 を回復、を別途ユーザー合意の上で実施する。
